# Prompting Guide

Claude Code는 `CLAUDE.md`(루트) + 작업 중인 패키지의 `CLAUDE.md`를 세션마다 자동으로 읽는다. 그래서 프로젝트 배경, 팀 구성, 규칙은 매번 다시 설명할 필요가 없다. 프롬프트에는 **"이번 세션에서 결정/구현해야 할 구체적인 것"만** 적으면 된다.

## 공통 원칙

- **어느 Phase/Step인지, 어느 패키지인지 먼저 명시한다.** ([ROADMAP.md](ROADMAP.md) 기준) → Claude가 범위를 정확히 잡는다. **Phase 하나가 보통 세션(채팅) 하나의 단위**이고, 그 안의 Step들은 같은 세션에서 순서대로 같이 처리한다.
- **문서에 이미 있는 내용은 반복 설명하지 않는다.** (팀 구성, 브랜치 규칙, 토픽 이름 등 — 이미 CLAUDE.md/docs에 있음)
- **세션을 어느 디렉토리에서 시작하는지가 중요하다.** 자기 패키지(`src/mov_stt/` 등)에서 시작하면 그 패키지의 `CLAUDE.md`가 같이 로드된다.
- **바로 "구현해줘/바꿔줘"로 맡기지 않는다.** 먼저 전체 작업계획(뭘 어떤 순서로 할지)을 제시하게 하고, 승인한 뒤 하나씩 같이 의논하면서 진행한다. 규모가 크면 Claude Code의 Plan Mode를 써도 좋다.
- **스텁 → 실구현으로 바꾸는 작업이면 "지금까지는 스텁이었다"는 걸 말해준다.** 그래야 뭘 유지하고 뭘 새로 짜야 하는지 헷갈리지 않는다.
- **INTERFACES.md(계약)를 바꿔야 할 것 같으면, 바꿔도 되는지 먼저 물어보라고 요청한다.** (Claude가 임의로 계약을 바꾸지 않게)

## Phase별 예시 프롬프트

### Phase 0 — 규칙설계
```
docs/ROADMAP.md의 Phase 0, Step 2(인터페이스 규칙+FSM+노드 구조)부터 시작할 거야.
Step 1(문서화 인프라)은 이미 끝났어.
docs/INTERFACES.md 템플릿과 docs/ARCHITECTURE.md의 노드 다이어그램/FSM 섹션을 채우려고 해.

- FSM 상태는 터치스크린 시나리오 기준으로: 대기 → 말하기 버튼 → 음성인식중
  (파형 애니메이션) → 인식결과 확인/다시말하기 → 이동중(목적지명/진행상태/
  남은거리/취소버튼) → 도착(새 장소 안내/처음화면) → 오류.
- 노드 다이어그램은 docs/TEAM.md 패키지 8개 기준으로.
- 토픽/서비스/액션 이름과 메시지 타입까지 구체적으로.

바로 채우지 말고, 먼저 전체적으로 어떻게 구성할지 계획(안)을 제시해줘.
내가 확인하고 승인하면 그때 하나씩 같이 의논하면서 문서를 채우자.
계약 문서라 셋이 같이 리뷰해야 하니 커밋은 하지 마.
```

### Phase 1 — 워킹 스켈레톤 · 시뮬레이터
```
Phase 1 진행하려고 해. 테스트맵 기반으로 가짜 목적지 좌표 3~4개
(예: 스타벅스, 정문, 화장실)를 정하고, docs/INTERFACES.md 계약대로
각 mov_* 노드의 스텁(가짜 입출력)을 만들 거야.
목표는 시뮬레이터에서 "음성 목적지 입력 → 좌표 매핑 → Nav2 이동 →
도착 안내"가 가짜 데이터로 한 바퀴 도는 것.

바로 만들지 말고, 어떤 노드/파일을 어떤 순서로 만들지 계획부터 보여줘.
내가 승인하면 하나씩 같이 만들자.
```

### Phase 2 — 워킹 스켈레톤 · 실기 (테스트맵)
```
Phase 2야. Phase 1 스켈레톤 로직은 그대로 두고, 시뮬레이터 대신
테스트맵 SLAM 지도(맵 파일: <경로>)로 실제 로봇에서 같은 e2e를
재현하려고 해.

뭘 바꿔야 할지(launch/파라미터) 먼저 계획을 보여주고, 내가 확인하면
하나씩 적용하자.
```

### Phase 3 — ECC 실측 SLAM 매핑
```
Phase 3 시작이야. 오늘 ECC <n>층 실측 SLAM 주행 예정인데, cartographer
설정에서 루프클로저 정확도를 높이려면 어떤 파라미터를 조정하면 좋을지
후보와 이유를 먼저 정리해줘. 내가 고르면 그걸로 적용하자.

주행 끝나면 생성된 맵으로 가짜 좌표를 ECC 실제 좌표로 교체할 건데,
이것도 같은 방식으로 — 계획 먼저 보여주고 승인하면 진행하자.
```

### Phase 4 — 병렬 실구현 (담당자별로 따로 세션)

**4-A 배 (`src/mov_dest_resolver`에서 시작)**
```
Phase 4-A 작업 중이야. INTERFACES.md의 자연어→좌표 서비스 계약대로,
사용자 발화 텍스트를 받아 ECC 맵 좌표 DB에서 가장 가까운 장소를 찾아
반환하는 실제 로직으로 바꾸려고 해. 지금까지는 스텁이 고정값만 반환했어.

바로 코드 바꾸지 말고, 어떤 순서로(DB 스키마 → 매칭 로직 → 상대좌표
처리 등) 구현할지 계획부터 제시해줘. 승인하면 하나씩 같이 하자.
```

**4-B 최 (`src/mov_navigation`에서 시작)**
```
Phase 4-B야. 동적 장애물 환경에서 기본 Nav2 DWB보다 나은 로컬 플래너
후보를 젯슨 오린 나노 리소스 제약 고려해서 조사해줘.

후보별 장단점을 먼저 정리해서 보여주고, 내가 하나 고르면 그걸 붙이는
작업을 하나씩 같이 하자.
```

**4-C 곽 (`src/mov_stt`에서 시작)**
```
Phase 4-C, 지금까지 마이크 입력을 고정 텍스트로 흉내내던 스텁을
실제 마이크 캡처 + STT(Gemini API 또는 온디바이스) 연동으로 바꾸려고 해.
출력 토픽은 INTERFACES.md의 /stt/result 그대로 유지할 거야.

먼저 두 방식(온디바이스 vs API)의 장단점과 구현 순서를 계획으로
보여주고, 내가 승인하면 하나씩 같이 만들자.
```

### Phase 5 — 통합 & 젯슨 포팅
```
Phase 5야. 지금까지 각자 만든 mov_* 실구현들을 ECC 맵 위에서
통합하려고 해.

먼저 통합 순서/체크리스트(뭐부터 붙이고 어떤 순서로 테스트할지)를
계획으로 보여줘. 승인하면 하나씩 같이 통합·디버깅하자.
빌드 에러/토픽 미스매치는 INTERFACES.md 기준으로 원인 찾아줘.
다 되면 젯슨 오린 나노용 launch/파라미터 세팅도 같은 방식으로 정리하자.
```

### Phase 6 — 실전 테스트
```
Phase 6, 실전 데모 준비야. 지금까지 나온 실패 로그/버그를 정리해서
우선순위와 함께 체크리스트 초안을 보여줘. 내가 확인하고 순서를
정하면 하나씩 같이 처리하자.
```
